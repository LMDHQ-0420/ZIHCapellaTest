## 已证实的工具逻辑问题

1. **节点状态判断过于严格。** c59、c23 实际显示 `mixed-`，工具只接受完全相等的 `mixed`，因此直接跳过；c119、c6 后来也因此被跳过。`-` 是 backfill 调度器的规划标记，不等于 DOWN/DRAIN。它也不保证有空闲 GPU；修复后仍需核对实际资源和调度结果。[Slurm 官方状态说明](https://slurm.schedmd.com/sinfo.html)
2. **环境门控把四卡资源可得性混入单卡软件判断。** 单卡环境已通过，但 `environment_matrix` 用单卡、四卡结果的逻辑与设置 `standalone=false`，使第 5、6 阶段完全跳过。这里没有单卡 Python/PyTorch/CUDA 失败证据。
3. **定向节点没有在资源准入失败后停止重复等待。** c113 的 16 个变体都等待同样的不可得资源；c148 则重复相同的通用预检查拒绝。应保留未验证项并换候选节点，而不是将队列等待当成文件系统实验。
4. **覆盖标记过于乐观。** 原报告第 2 阶段标 PASS，实际只证明三个自动基线通过，六节点矩阵未完成；原 findings 也没有把 24 个 REJECTED 列入未验证。这些标记不能替代逐实验记录。

这些是客户端工具问题，不是服务器训练并发故障的证据。
